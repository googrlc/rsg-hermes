# Commercial intake → ACORD → CRM → AMS — build spec

Consolidates the intake/ACORD flow decisions. Grounded in the real licensed
templates (see `field-catalogs/`) and the existing Command Center code. This is
the agreed design; PRs implement it in phases at the bottom.

## Source of truth

- **NowCerts (AMS)** — the system of record for who the client is and what they
  carry. All commercial fills the AMS from the one approved record.
- **CRM `opportunities`** — the deal pipeline, **derived from** NowCerts, plus one
  opportunity per **line of business the agent chooses to market**.
- **ACORD PDFs** — an **on-demand export** to send an underwriter. Not a mandatory
  step; generated by choice.
- **Supabase** — staged intake, provenance, the agent's answers, approval state,
  and the queued write plan. No background Supabase→NowCerts sync; Hermes writes
  the AMS directly from an approved plan.

## The flow

```
evidence ─▶ canonical SubmissionObject ─▶ review (data + Y/N questions) ─▶ LOCK
                                                                            │
                    ┌───────────────────────────────────────────────────────┤
                    ▼                                                        ▼
        Supabase staged plan (PREVIEW)                        ACORD pack (on demand)
                    │  approve                                 fill 125 + selected
                    ▼                                          supplementals → PDFs
        Hermes ─▶ NowCerts write ─▶ read-back verify ─▶ receipt (VERIFIED)
                    │
                    ▼
        one opportunity per checked line of business
```

ACORD generation and the AMS write are **parallel consumers of the locked
record** — ACORD completion never gates the AMS write.

## 1. The 125 is the hub — select lines + attachments

The agent selects, from the extensible catalog (`acord_forms.yaml`):

- **Lines of business** → each checks its **125 line-of-business box**, attaches
  its supplemental form (GL→126, Property→140, …), and **creates one opportunity**
  for that line.
- **Supplementals/attachments** → check the matching **125 attachment indicator**
  (e.g. Statement of Values, Contractors Supplement).

The catalog is data-driven: a form with `filler: null` is still selectable — it
checks the 125 box and creates the opportunity today; its PDF filler is added
later. That is the "place to store and add more accords and supplementals".

## 2. Checkbox handling — three classes

The 125/126 has **208 checkbox fields carrying tooltip (`/TU`) questions**. They
split into three classes; the split is the core of this design:

| Class | Source | Example fields | Behavior |
|---|---|---|---|
| **Structural** | selection | LOB boxes, attachment indicators, quote status | Set by what the agent selected in §1 |
| **Data-derived** | the record | entity type, business type (from NAICS), owner/tenant, occurrence-vs-claims-made (from `coverage_request`) | Set deterministically from the canonical record |
| **Agent questions** | must be answered | `LossHistory_NoPriorLosses`, `FormalSafetyProgram_OSHA`, `GeneralLiability_MedicalPayments_CoverageAvailable`, `SwimmingPool_*`, deductible-requested, UM/UIM | **Prompted for the agent to answer in review** |

**The agent-question boxes are prompted, with the form's own `/TU` text as the
question, and must be resolved (yes / no / n-a) before the record can be staged to
Supabase or written to the AMS.** Questions are auto-derived from the template's
tooltips — not hand-authored — so a new form's questions appear automatically.

Every answer is stored on the canonical record with provenance (who answered,
when), the same way data fields carry evidence.

## 3. Gate order

```
data complete + conflicts resolved + agent questions answered
        └─▶ LOCK ─▶ Supabase PREVIEW ─▶ approve ─▶ AMS write ─▶ read-back ─▶ VERIFIED
```

The submission cannot advance to Supabase staging (and therefore not to the AMS)
while any **required** agent question is unanswered. "Required" = the question is
in scope for a selected line/section (GL questions only gate when GL is selected).

## What already exists (reuse, don't rebuild)

- **One opportunity per LOB → `opportunities`** — `router.py` (`intake_crm`) +
  `intake_executor.map_opportunity_row`.
- **Insured → NowCerts, gated + read-back verify** — `intake_ams`,
  `ams/writeback.py`.
- **CRM ← NowCerts sync** — `--sync-nowcerts`, canonical book.
- **Real 125/126/140 fillers + combined pack** — `deliverables/acord125|126|140`,
  `acord_commercial_pack`, verified against the licensed templates (PR #299).
- **Approval/review state machine** — `command_center/service.py`,
  `outbound_sync_queue`.

## What is new

- `acord_forms.yaml` + a registry loader — the extensible form store.
- Selection model: checked LOBs → 125 boxes + supplementals + opportunity drafts.
- Multi-LOB 125 checkbox fill (today only the single `sub.lob`).
- **Checkbox question model**: derive agent-questions from `/TU`, classify
  structural/derived/question, store answers with provenance, gate on required
  answers before staging.
- On-demand "generate ACORD copies for underwriter" action (per building for 140).

## Phased delivery

- **P1 — form store + selection** (no AMS/AI): `acord_forms.yaml` + registry;
  selection → 125 multi-LOB checkboxes + supplemental list; per-checked-LOB
  opportunity drafts (feed the existing `intake_crm` path). Pure + tested.
- **P2 — on-demand ACORD export**: generate the real PDFs (combined 125/126 + one
  140 per building) behind an explicit action; store filled PDFs; never auto-send.
- **P3 — checkbox questions**: extract `/TU` questions, classify, add to the review
  model, store answers with provenance, enforce the "answered before staging" gate.
- **P4 — Supabase→AMS plan**: map the locked record (data + answers) to the staged
  plan; duplicate search; approve; write; read-back receipt (extends the existing
  `intake_ams`/writeback path).

Each phase is independently shippable; P1 unblocks the selection UI, P3 delivers
the Y/N-question requirement.
